# Google integrations — phases 13–14

Phase 13 connects Google Calendar and Gmail as separate optional, read-only context sources. Phase 14 adds narrowly scoped Calendar event creation after explicit per-action approval. The feature remains dormant until `GOOGLE_INTEGRATIONS_ENABLED=true`, all server-only credentials are configured and the signed-in email appears in `GOOGLE_INTEGRATION_TEST_USERS`. A signed ten-minute HttpOnly state binds the exact selected services, requested Calendar access level and private OAuth return path to the Avenli account that started it. The callback accepts only the corresponding allowlisted scopes and rejects a different Google email.

The public `integrations` table stores only connection status, email, authorized scopes, independently enabled services and timestamps. Provider access and refresh tokens are encrypted with AES-256-GCM using `INTEGRATION_ENCRYPTION_KEY` and stored in `private.integration_credentials`. Authenticated users cannot query the private schema. Service-role functions expose only bounded credential operations to the server. Row-level security limits connection metadata and audit events to their owner.

The Calendar preview reads at most fifty non-cancelled events from the next one to thirty days. Gmail searches at most ten messages and requests the metadata representation with Subject, From and Date headers plus the provider's short snippet; message bodies are not requested. Audit rows record the operation, result count and calendar window. Gmail query text, provider tokens and returned content are not written to the audit log.

Event proposals do not contact Google. Once the user reviews the exact event and confirms creation, Avenli uses the incremental `calendar.events.owned` grant to create it in the primary calendar. No attendees are included and no invitations are sent. The action UUID maps to a deterministic provider event ID so retries cannot create duplicates. See [`actions.md`](actions.md) for approval, idempotency and audit details.

Switching off Calendar or Gmail immediately prevents Avenli from calling that service and records the preference change. Google may retain the previously granted provider scope until the user chooses **Disconnect Google**; full disconnect first attempts Google's token-revocation endpoint, then always deletes the local credential and marks the connection disconnected. Account export includes connection metadata and audit rows but never credentials. Account deletion cascades both public integration records and the private credential row.

Before enabling production, apply `20260913030000_google_integrations.sql`, `20260913040000_optional_google_services.sql`, `20260914000000_preserve_google_authorizations.sql` and `20260914010000_external_actions.sql`; set the three server-only Google variables; and enable the Gmail and Calendar APIs in the existing Google Cloud project. Add the two read-only scopes and `calendar.events.owned` to the OAuth consent configuration and complete any Google verification required for external users. Then verify separate authorization, enable/disable, account mismatch, Calendar read, Gmail search, contextual Calendar write authorization, event creation, idempotent retry, expired-token refresh, full disconnect and reconnect on `avenli.vercel.app`.
